# MSDS Extraction Cleanroom — 프로젝트 방향성

작성일: 2026-07-11
상태: 사용자 승인 후 적용되는 상위 프로젝트 기준

## 1. 프로젝트 사명

다양한 형식의 MSDS에서 제품명과 3섹션 구성성분을 추출하고, 유효한 CAS 번호와
원문 함유량을 사람이 검증할 수 있는 형태로 제공한다.

이 프로젝트의 목적은 “가능한 값을 많이 출력하는 것”이 아니라 “근거가 있는
값만 출력하고 불확실성을 숨기지 않는 것”이다.

핵심 원칙:

> 틀린 초록불보다 설명 가능한 노란불이 낫다.

## 2. 대상 사용자와 사용 장면

주 사용자:

- 작업환경측정 및 유해인자 관리 담당자
- MSDS 구성성분을 검토하고 MES 자료와 연결하는 실무자
- 추출 결과를 수정·검증·내보내야 하는 관리자

주요 사용 흐름:

1. PDF를 불러온다.
2. 제품명과 3섹션 CAS·함유량을 추출한다.
3. 근거와 신호등을 확인한다.
4. 사람이 필요한 부분만 교정한다.
5. KOSHA·노출기준·MES 자료와 결합한다.
6. 검증 결과를 저장하거나 내보낸다.

## 3. 제품 성공 기준

### 3.1 정확성

승인된 골든 데이터에서:

- 제품명 허용 정답 일치율: 100%
- CAS 순서·집합 정확도: 100%
- 함유량 정규화 정확도: 100%
- 3섹션 밖 CAS 오탐: 0건
- CAS 없는 성분에 대한 CAS 환각: 0건
- False Green: 0건

### 3.2 재현성

- 동일 PDF·동일 환경에서 로컬 추출 결과가 반복 가능해야 한다.
- Python과 핵심 OCR 의존성 버전을 잠근다.
- 원본 PDF는 SHA-256으로 동일성을 확인한다.
- 캐시를 비운 상태에서도 검증 결과가 유지되어야 한다.

### 3.3 설명 가능성

각 결과는 가능한 범위에서 다음을 남긴다.

- 추출 출처: ODL, 밀도 클러스터링, OCR, AI
- 원본 페이지
- 선택된 함량과 경쟁 후보
- 신호등이 낮아진 이유
- 외부 AI fallback 사용 여부

### 3.4 운영성

- 실패 문서 한 건이 전체 배치를 중단시키지 않는다.
- 오류 문서는 격리되고 재처리할 수 있어야 한다.
- 비밀키와 업무 데이터는 Git에 포함하지 않는다.
- 외부 AI 호출 횟수·시간·비용을 계측할 수 있어야 한다.

## 4. 범위

현재 필수 범위:

- 1섹션 제품명
- 3섹션 유효 CAS 번호와 함유량(구성성분명 제외)
- 디지털 PDF와 순수 스캔 PDF
- 한국어·영어 혼합 문서
- 표, 수직 카드, 다중 페이지 구성성분
- 로컬 추출과 외부 AI fallback
- 신호등 및 사람이 검토할 수 있는 결과

현재 비범위:

- MSDS 전체 16개 섹션의 완전 구조화
- 디지털·OCR 문서의 전체 페이지 판독 또는 전체 문서 AI 전송
- 3섹션 구성성분명 추출·정제·저장
- 화학물질 규제 판단의 자동 법률 결론
- 사람이 승인하지 않은 CAS 생성
- 골든 근거 없이 특정 업체 문서만을 위한 하드코딩
- 13/13 달성 전 대규모 GUI 개편

## 5. 기술 방향

### 5.1 처리 우선순위

1. 원문에 근거한 로컬 결정론적 추출
2. 서로 다른 로컬 추출기의 후보 교차 검증
3. 품질 판정 및 충돌 감지
4. 로컬 결과가 불충분한 경우에만 외부 AI
5. 불확실하면 노란불 또는 빨간불

### 5.2 목표 구조

현재 실행선:

smu_gui.py → msds_core.py → msds_engine_v6.py → msds_utils_v3.py

목표 논리 구조:

문서 판별
→ 섹션 탐색
→ 제품명 추출
→ 구성성분 후보 추출
→ 후보 병합·우선순위
→ 품질 검증
→ 표준 결과 계약

장기 모듈 후보:

- document_classifier
- section_locator
- product_extractor
- component_extractors
- candidate_resolver
- quality_control
- result_schema

구조 분리는 골든 13/13을 달성한 뒤 동작 보존 테스트와 함께 진행한다.

## 6. 단계별 로드맵

### Gate 0 — Cleanroom 기반 확립

상태: 완료

- 독립 폴더와 Git 저장소
- Private GitHub 원격
- Python 3.12 환경
- 의존성 잠금
- 승인 골든 13건
- 회귀 하네스

### Gate 1 — 핵심 회귀 13/13

상태: 진행 예정

- 015 결합 CAS 노이즈 제거
- 032 범위 우선순위 복구
- 040 함량 열 판별 복구
- 047 다중 CAS·함량 매핑 복구
- 기존 스캔본 005·046 보호

통과 조건:

- 골든 실제 엔진 회귀 13/13
- 오프라인 엔진 회귀 14/14
- 단위 테스트 전부 통과

### Gate 2 — 현행 사양 확정

결정할 정책:

- 함량 합계 상한
- 원문 100% 초과 처리
- False Green 신호등 정책
- 제품명 파일명 보정
- 제품명 AI 호출 생략
- 추출기 충돌 우선순위

통과 조건:

- 각 정책에 예시 입력과 기대 출력이 존재
- 골든 영향도가 기록됨
- 사용자가 결정하고 DECISION_LOG에 남김

### Gate 3 — 엔진 구조 안정화

- 거대 엔진의 책임 경계 분리
- 표준 결과 스키마 도입
- 후보 출처·근거 메타데이터 통일
- 전역 상태와 숨은 캐시 의존 제거
- GUI와 엔진 계약 테스트 추가

통과 조건:

- 기능 변경 없이 골든 13/13 유지
- 모듈 단위 테스트 가능

### Gate 4 — 검증 데이터 확대

- 30건: 제조사·언어·레이아웃 다양화
- 50건: 디지털·스캔 균형
- 100건 이상: 실제 운영 적합성 평가

모든 사례는 사람 승인 정답, 원본 해시, 실패 태그를 가진다.

통과 조건:

- 문서 유형별 정확도와 실패율 산출
- False Green 0건
- 반복 실패 유형이 테스트로 환류

### Gate 5 — 운영·배포 준비

- 설치·업데이트 절차
- 캐시·설정 이전 정책
- 실패 격리와 재처리
- 로그와 비용 계측
- 릴리스 전 자동 회귀
- 이전 버전 롤백
- GUI smoke test

통과 조건:

- RELEASE_CHECKLIST 전 항목 통과
- 새 PC 또는 깨끗한 환경에서 설치 재현
- 사용자 승인 후 버전 태그 생성

## 7. 품질 운영 방식

오류 처리 순환:

1. 실제 실패를 수집한다.
2. 원본과 사람이 정답을 확정한다.
3. 최소 재현 테스트를 만든다.
4. 가장 좁은 범위로 수정한다.
5. 집중 테스트와 전체 골든을 실행한다.
6. 원인과 해결을 기록한다.

금지 사항:

- 테스트 없이 예외 규칙 추가
- 엔진 결과에 맞춘 골든 정답 변경
- 실패 이유를 숨긴 초록불
- 외부 AI 응답을 근거 확인 없이 채택
- 회귀 실패 상태에서 main 병합
- 디지털 PDF 또는 이미지/OCR PDF의 모든 페이지 판독
- 섹션 경계가 불명확하다는 이유로 전체 문서를 fallback 판독
- 3섹션 구성성분명 추출 및 이름 기반 CAS 추정·생성

## 8. 의사결정 체계

사용자 승인 필요:

- 제품 정책 변경
- 골든 정답 변경
- 외부 API 공급자·비용 정책 변경
- 결과 스키마의 호환성 파괴
- main 병합과 정식 릴리스

개발 절차로 처리 가능:

- 승인 정책을 보존하는 버그 수정
- 테스트·진단 도구·문서 보강
- 비밀정보 제외와 안전한 의존성 고정

모든 주요 결정은 DECISION_LOG.md에 날짜, 배경, 선택, 영향, 검증 방법을 남긴다.

## 9. 문서 우선순위

1. PROJECT_DIRECTION.md — 목표와 장기 방향
2. CURRENT_SPEC_DRAFT.md 또는 승인 후 CURRENT_SPEC.md — 현재 제품 규칙
3. NEXT_IMPLEMENTATION_PLAN.md — 당장 실행할 전술
4. 골든 데이터와 회귀 보고서 — 검증 증거
5. 역사 문서 — 과거 장애와 참고 기록

상위 문서와 충돌할 경우 역사 문서의 과거 표현을 현재 규칙으로 사용하지 않는다.
